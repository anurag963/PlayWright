Automation Exercise API Framework

API-level tests for automationexercise.com that cover the scenarios automated in the POM framework. No browser starts: each test sends HTTP requests through Playwright's request fixture, and the whole suite runs in under half a minute.

37 tests5 spec files7 clients14 REST endpoints8 storefront endpoints~26 s full run

Overview

The site offers a public JSON API for products, brands, search and accounts. It has no API for the cart, login session, checkout or contact form. Those flows run on server-rendered pages and small AJAX endpoints. The framework covers both with two kinds of client:

  • REST clients call /api/* and parse the JSON reply.
  • Storefront clients call the same URLs the browser uses. They keep session cookies, send the CSRF token Django forms require, and read results out of the returned HTML.

The rest follows the POM framework's patterns:

  • Fixtures give each test ready-made clients and test users, so specs never call new CartClient(request).
  • One method per endpoint, named after what it does: searchProduct(term), cart.add(id, qty), checkout.pay(card).
  • Every request is an Allure step, with the payload and response attached and passwords, card numbers and tokens masked.
  • A .env file holds the base URL and the shared login. It is gitignored.

Request pipeline

Every request, REST or storefront, ends in BaseClient.send(). Form posts take one extra round trip first, to fetch a CSRF token from the page that holds the form.

flowchart LR
  A["Spec calls a client method
e.g. checkout.pay(card)"] --> B{"Storefront form?"}
  B -- "yes" --> C["GET the form page
read csrfmiddlewaretoken"]
  C --> D["Add token + Referer header"]
  B -- "no" --> E["BaseClient.send()"]
  D --> E
  E --> F["Allure step: METHOD path
attach masked request"]
  F --> G["request.fetch()
follows redirects, keeps cookies"]
  G --> H["Attach response
JSON always, HTML if short"]
  H --> I{"Which client?"}
  I -- "RestClient" --> J["Parse JSON
return httpStatus + body"]
  I -- "WebClient" --> K["Return status, final URL, HTML
parsed by htmlParser"]

The final URL matters: a successful payment redirects to /payment_done/{amount}, and checkout.pay() reads the order total from it.

The responseCode rule

The site's API answers HTTP 200 to every request, even failed ones, and labels its JSON as text/html. The real outcome is the responseCode field in the body. A test that only checked the HTTP status would pass for a failed request.

flowchart LR
  R["Response"] --> H{"HTTP status = 200?"}
  H -- "no" --> F1["fail: transport error"]
  H -- "yes" --> C{"body.responseCode
= expected?"}
  C -- "no" --> F2["fail: shows HTTP, code and message"]
  C -- "yes" --> M{"message given?"}
  M -- "no" --> P["pass"]
  M -- "yes" --> MM{"body.message
= expected?"}
  MM -- "yes" --> P
  MM -- "no" --> F2

The custom matcher toHaveResponseCode in the fixtures file runs this check:

Response from POST /api/createAccount

HTTP/2 200
content-type: text/html

{ "responseCode": 400,
  "message": "Email already exists!" }

Assertion in auth.api.spec.ts › TC5

expect(
  await accountApi.createAccount(duplicate)
).toHaveResponseCode(
  400, 'Email already exists!'
);

Response shapes are checked separately with toMatchObject(productSchema). A missing field or a wrong type fails the test; extra fields are allowed so additions to the API don't break the suite.

Code walkthrough

1. A spec asks for what it needs

Fixture names in the test's parameters decide what gets built. Here the test gets four clients and a throwaway user that already exists on the site.

  productsApi, auth, cart, checkout, apiUser,

  const [first, second] = (await productsApi.getAllProducts()).body.products;
  await auth.login(apiUser.email, apiUser.password);
  await cart.add(first.id, 2);
  await cart.add(second.id);
  const order = await checkout.pay(createCard());
  expect(order.amount).toBe(String(expectedTotal));
  ...
});

2. The fixture builds and cleans up

Code before use() is setup; code after it is teardown. Teardown runs even if the test fails. All clients share the test's request, so they share one session.

cart: async ({ request }, use) => use(new CartClient(request)),

apiUser: async ({ accountApi }, use) => {
  const user = createUser();                     // unique email per run
  await accountApi.createAccount(user);          // setup via API
  await use(user);                               // test runs here
  await accountApi.deleteAccount(user.email, user.password);  // teardown
},

3. The client hides the HTTP details

pay() doesn't know about tokens or headers. submitForm() in WebClient fetches the CSRF token and sets the Referer.

export class CheckoutClient extends WebClient {
  async pay(card: CardData) {
    const page = await this.submitForm('/payment', '/payment', {
      name_on_card: card.nameOnCard,
      card_number: card.cardNumber,
      ...
    });
    return {
      amount: page.url.match(/\/payment_done\/(\d+)/)?.[1] ?? null,
      text: pageText(page.html),
    };
  }
}

Test users

Same three kinds of user as the UI framework, so tests that delete an account never touch the shared one:

envUser

Your account from .env. Shared by all runs and never deleted.

TC2, TC3, TC4, TC5

apiUser

Created through /api/createAccount before the test, deleted after it.

TC2b, TC16, TC20, TC23, TC24, update account

newUser

Unique data only; the test registers it itself. Deleted after the test in case the test failed early.

TC1, TC14, TC15

Each test also gets its own request context, so its cookies, and with them its cart and login, are never shared with another test running in parallel.

Design decisions

  • A custom matcher for responseCode.Every API reply is HTTP 200. toHaveResponseCode checks the status, the body's code and the message in one assertion, and its failure message shows all three.
  • Storefront flows go through the site's own URLs.Cart, login and checkout have no JSON API. Calling /add_to_cart, /login and /payment directly covers TC12 to TC24 without a browser.
  • CSRF is handled once, in WebClient.Django rejects a form post without the page's token, and over HTTPS it also checks the Referer. submitForm() does both, so no client repeats it.
  • The guest cart is merged by opening the cart.Items added before login only join the user's cart when /view_cart is opened. TC14 opens the cart before checkout, as the UI test does.
  • TC6 checks that the contact form is accepted.The "Success!" banner is drawn by JavaScript, and the server returns the same page either way. The test checks the multipart POST gets a 200, and that one without a token gets a 403.
  • Regexes instead of an HTML parser.The site's cart and address markup is small and stable. A dozen targeted patterns in htmlParser.ts avoid a new dependency.
  • Secrets are masked in reports.Fields named like password, card_number, cvc or csrfmiddlewaretoken show as *** in Allure attachments.

Adding tests

A test on an existing endpoint

  1. Open the matching spec in specs/, or create specs/<area>.api.spec.ts.
  2. Import test and expect from ../fixtures/apiFixtures.
  3. Name the clients and user you need in the test's parameters.
  4. Call client methods. Use toHaveResponseCode for REST replies and a schema from models/schemas.ts for shapes.

A new endpoint

  1. JSON endpoint: add a method to the client in clients/api/ that returns this.call<Body>(method, path, options), and add the body type to models/types.ts.
  2. Page or form: add a method in clients/web/ using getPage() or submitForm(), and an extractor in htmlParser.ts if the result is in the HTML.
  3. A new client class gets a one-line fixture in fixtures/apiFixtures.ts.
// clients/api/ProductsApi.ts
getProductById(id: number) {
  return this.call<ProductBody>('GET', `/api/product/${id}`);
}

// fixtures/apiFixtures.ts
type ApiFixtures = { ...; ordersApi: OrdersApi };
ordersApi: async ({ request }, use) => use(new OrdersApi(request)),

vs UI framework

The same test case in both frameworks. The UI version drives six pages; the API version calls the endpoints those pages use.

tests/Framework (UI spec)

test('TC17: Remove Products From Cart',
  async ({ homePage, productsPage, cartPage }) => {
  await homePage.header.goToProducts();
  await productsPage.addProductToCartAt(0);
  await productsPage.continueShopping();
  await homePage.header.goToCart();
  await cartPage.removeProduct(1);
  await expect(cartPage.emptyCartMessage)
    .toBeVisible();
});

tests/ApiFramework (API spec)

test('TC17: Remove Products From Cart',
  async ({ cart }) => {
  await cart.add(1);
  expect((await cart.view()).rows
    .map((r) => r.productId)).toEqual([1]);

  expect(await cart.remove(1))
    .toBe('Cart removed');
  expect((await cart.view()).isEmpty)
    .toBe(true);
});
