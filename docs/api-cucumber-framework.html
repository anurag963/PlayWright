Automation Exercise API Cucumber Framework

The API framework with a Gherkin layer on top. API checks are written as plain-language scenarios; step definitions call the same REST and storefront clients. No browser starts.

5 feature files32 scenarios41 tests72 step definitions0 browsers~29 s full run

Overview

Built on playwright-bdd, like the UI Cucumber framework. Feature files become ordinary Playwright tests, so everything from the API framework keeps working:

  • REST clients for /api/* and storefront clients for login, cart, checkout and contact.
  • The toHaveResponseCode matcher for an API that always answers HTTP 200.
  • Allure steps per request, with passwords, card numbers and CSRF tokens masked.
  • Test users created and deleted through the API, parallel workers and retries.

What Gherkin adds: API behaviour a tester or product owner can read and review, without reading TypeScript.

@TC1 @smoke
Scenario: Register a new user
  Given I have details for a new user
  When I create the user's account
  Then the response code is 201 with message "User created!"
  When I delete the user's account
  Then the response code is 200 with message "Account deleted!"

Sentence to request

A "When" step sends one request through a client and stores the reply in ctx. A "Then" step checks what was stored. Steps never build URLs or parse HTML themselves.

Feature file

When I search for "Jeans"
Then the response code is 200
And every product name contains "Jeans"

Step definitions

When('I search for {string}',
  async ({ ctx, productsApi }, term) => {
    ctx.response = await productsApi.searchProduct(term);
    ctx.products = ctx.response.body.products ?? [];
  });

The responseCode steps

The site's API answers HTTP 200 to every request and puts the real outcome in the body's responseCode. Two shared steps check it, using the toHaveResponseCode matcher:

StepChecks
Then the response code is {int}HTTP 200 and responseCode
Then the response code is {int} with message {string}HTTP 200, responseCode and message

They read ctx.response, the last REST reply. Any "When" step that calls the REST API sets it, so the same two steps work after a search, a login check, an account create or a 405 probe.

Context & users

Each scenario gets a fresh ctx, Cucumber's "World". "When" steps write to it; "Then" steps read from it.

interface ScenarioContext {
  user?: Account;          // who the scenario acts as
  userData?: UserData;     // full data for API-created or new users
  response?: ApiResult;    // last REST reply, checked by "the response code is ..."
  products: Product[];     // last product list or search
  brands: Brand[];
  added: { id; quantity; product? }[];  // what went into the cart
  cartRows?: CartRow[];    // parsed /view_cart
  login?: LoginResult;     // storefront login result
  page?: { status; url?; text? };       // last page opened or form submitted
  checkout?; order?; invoice?; contactForm?;
}

A step that needs data an earlier step should have set fails with a message naming that step, for example No API response yet. Add a "When I ..." step that calls the API first.

Scenario Outline for negative cases

Three unsupported methods, one scenario. Each row is a separate test:

  @methods
  Scenario Outline: <method> <endpoint> is not supported
    When I send an unsupported <method> request to "<endpoint>"
    Then the response code is 405 with message "This request method is not supported."

    Examples:
      | method | endpoint          |
      | POST   | /api/productsList |
      | PUT    | /api/brandsList   |
      | DELETE | /api/verifyLogin  |

The step maps "METHOD endpoint" to a client call through a lookup table, and fails with the list of known pairs if a row names one it doesn't know.

Data tables

    When I update the user's account with:
      | company  | Updated Labs      |
      | city     | Mysore            |
      | address1 | 10 Downing Street |

    Then the brands include:
      | Polo |
      | H&M  |

Update tables are read with table.rowsHash() and unknown field names are rejected. The updated user is kept in ctx, so a later "user details match" or checkout address step compares against it.

    Adding scenarios

    1. Write the scenario in the matching feature file, reusing sentences from the step catalogue.
    2. Run npm run bddgen:api. For any sentence without a definition it fails and prints a snippet.
    3. Implement the step with a client call. Store REST replies in ctx.response so the shared responseCode steps work after it.
    4. If the endpoint is new, add a method to the client first; keep HTTP details out of steps.
    5. Tag the scenario and run it with --grep.
    // steps/products.steps.ts
When('I request product {int}', async ({ ctx, productsApi }, id: number) => {
  ctx.response = await productsApi.getProductById(id);   // new client method
});
// the feature can then reuse: Then the response code is 200

    Pitfalls

    • Checking only the HTTP status.Every reply is HTTP 200. Use the responseCode steps, which check the body as well.
    • A "When" step that forgets ctx.response.The next "Then the response code is …" step then checks the previous reply, or fails with "No API response yet".
    • Guest cart after login.The site merges a guest cart into the user's cart when /view_cart is opened. TC14 opens the cart before checkout for that reason.
    • The contact form's success message.It is drawn by JavaScript; the server returns the same page either way. TC6 checks the POST is accepted and that one without a CSRF token gets a 403.
    • Running stale tests.After editing a feature, run npm run bddgen:api; plain npx playwright test runs the last generated files.
    • Scenarios listed twice in VS Code.The suite is already in the root config. Don't also enable this folder's own config.
