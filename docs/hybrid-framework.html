Automation Exercise Hybrid Framework

UI and API testing in one framework for automationexercise.com. A test can set up state over HTTP, act in the browser and check the result in either layer, all in the same session.

22 tests4 spec files9 page objects6 API clients1 shared session~45 s full run

Overview

The POM framework tests what a user sees. The API framework tests what the server does. Neither can check that the two agree: that the product the API lists is the one the page shows, or that a form filled in the browser saved what the API returns. The hybrid framework puts both layers in one test.

  • UI layer: the page objects and components from tests/Framework, unchanged apart from two read-out methods on ProductsPage.
  • API layer: the REST and storefront clients from tests/ApiFramework.
  • One session: the API clients run on the browser tab's own request context, so cookies, cart and login are shared.
  • One fixture file that hands a test both page objects and API clients, plus the test users.

The site's API has no endpoint for creating products; the catalogue is fixed. "Add a product via API" therefore means adding it to the cart over HTTP and checking it in the browser (HY1).

One shared session

Playwright gives every browser context its own request client, page.request. Unlike the standalone request fixture, it shares the context's cookie storage. Every API client in this framework is built on it:

// fixtures/hybridFixtures.ts
apiCart: async ({ page }, use) => use(new CartClient(page.request)),
apiAuth: async ({ page }, use) => use(new AuthClient(page.request)),

The site keeps the cart and the login in the session cookie, so whatever one layer changes, the other sees on its next request:

  T->>B: expect row for product 1, quantity 3

HY1 in miniature. The same mechanism works the other way: a click in the UI updates the session, and apiCart.view() sees it (HY2, HY3).

The public /api/* endpoints don't use the session, so productsApi and accountApi behave the same on this client as on any other.

Code walkthrough

1. Arrange over HTTP, assert in the browser (HY1)

test('HY1: Products added via API appear in the UI cart', async ({
  productsApi, apiCart, cartPage,
}) => {
  const [first, second] = (await productsApi.getAllProducts()).body.products;
  await apiCart.add(first.id, 3);
  await apiCart.add(second.id);

  await cartPage.open();
  expect(await cartPage.getRows()).toEqual([
    { name: first.name, price: first.price, quantity: '3', total: `Rs. ${...}` },
    { name: second.name, price: second.price, quantity: '1', total: second.price },
  ]);
});

2. Act in the browser, check the server (HY13)

await homePage.header.goToSignupLogin();
await registerUserViaUi(loginPage, signupPage, accountStatusPage, newUser);

expect(await accountApi.verifyLogin(newUser)).toHaveResponseCode(200, 'User exists!');
const { body } = await accountApi.getUserDetailByEmail(newUser.email);
expect(body.user).toMatchObject({ first_name: newUser.firstName, city: newUser.city, ... });

3. Compare both layers (HY6)

getListedProducts() reads every card's id, name and price in one call, so the comparison is a single toEqual:

const { products } = (await productsApi.getAllProducts()).body;
await homePage.header.goToProducts();

expect(await productsPage.getListedProducts())
  .toEqual(products.map(({ id, name, price }) => ({ id, name, price })));

4. Skip the login form

loginViaApi() posts the /login form over HTTP. The browser picks up the session on its next page load:

export async function loginViaApi(apiAuth: AuthClient, user) {
  const res = await apiAuth.login(user.email, user.password);
  expect(res.loggedInAs).toBe(user.name);
}

Design decisions

  • API clients use page.request, not the request fixture.The standalone fixture has its own cookie jar, so a cart filled there would never reach the browser. page.request belongs to the browser context and shares its cookies.
  • One test-data shape for both layers.The UI dropdown needs "March", the API needs "3". Test data keeps the UI form and AccountApi converts, so one UserData object registers through either layer and is compared in both.
  • Read-outs on the page object, not in specs.getListedProducts() and getSidebarBrands() live in ProductsPage and return plain data, so comparisons with the API are one toEqual and selectors stay out of specs.
  • Polling where the UI writes asynchronously."Add to cart" in the UI fires an AJAX request. HY2 uses expect.poll on the API cart so it waits for that request to land.
  • Ads are blocked for the tab only.The route that aborts ad requests applies to the browser. HTTP calls on page.request never load ads, so they need nothing.
  • Own copy of both layers.Like the other frameworks in this repo, the folder is self-contained. A fix to a page object or client must be copied to the framework it came from.

Adding tests

  1. Pick the pattern: API → UI, UI → API, or API = UI.
  2. Open the matching spec in specs/ and import test and expect from ../fixtures/hybridFixtures.
  3. Name the page objects, API clients and user you need. Use loginViaApi() when login is setup rather than the thing under test.
  4. When the UI must be read as data, add a read-out method to the page object that returns plain values.
  5. Give it the next HYxx id so Allure tags it.
test('HY21: Product removed via API disappears from the UI cart', async ({ apiCart, cartPage }) => {
  await apiCart.add(1);
  await cartPage.open();
  await expect(cartPage.rowByProductId(1)).toBeVisible();

  await apiCart.remove(1);
  await cartPage.open();
  await expect(cartPage.emptyCartMessage).toBeVisible();
});
