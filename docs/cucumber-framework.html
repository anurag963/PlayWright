Automation Exercise Cucumber Framework

The Page Object Model framework with a Gherkin layer on top. Test cases are written as plain-language scenarios; step definitions connect each sentence to the same page objects.

5 feature files27 scenarios28 tests79 step definitions4 reporters

Overview

The framework is built on playwright-bdd. It reads your .feature files, checks that every sentence has a step definition, and generates ordinary Playwright tests from them. Playwright then runs those tests.

Because the tests are still Playwright tests, everything from the POM framework keeps working:

  • Page objects, components and flows, unchanged.
  • Fixtures, including the API-created test users and the ad blocking.
  • Parallel workers, retries, traces, screenshots and video.
  • The Playwright HTML report and Allure, plus a Cucumber HTML report.
  • The VS Code test explorer, where each scenario is listed as a test.

The other common option, cucumber-js, brings its own runner. You would rebuild parallelism, browser setup, retries and reporting yourself, and lose Playwright's fixtures.

Generate & run

Running a scenario is a two-stage process. npm run test:cucumber does both stages.

  A["Edit a .feature file"] --> B["npx bddgen"]
  B --> C{"Every sentence has

  C -- "no" --> D["bddgen fails and prints
a code snippet"]
  D --> E["Add the step in steps/*.steps.ts"]
  E --> B
  C -- "yes" --> F["Writes .features-gen/*.spec.js"]
  F --> G["playwright test"]
  G --> H["Cucumber HTML
Playwright HTML

Generated files are gitignored and are recreated on every run. Never edit them; edit the feature or the step instead.

Sentence to code

Each sentence in a scenario is matched against step definition patterns. Quoted text and numbers become arguments; fixtures are requested by name, just like in a Playwright test.

Feature file

When I search for "Jeans"
Then the listing title is "Searched Products"
When I add the product at position 1 to the cart

Step definition

When('I search for {string}',
  async ({ productsPage }, term) => {
    await productsPage.search(term);
  });

What each part does

PartMeaning
'I search for {string}'The pattern (a Cucumber Expression). {string} matches quoted text, {int} a whole number, {word} one word. product(s) makes the "s" optional.
{ productsPage }Fixtures this step needs. They are created for the scenario the same way as in a Playwright test.
termThe value captured by {string}, here "Jeans".
When / ThenImported from fixtures/pomFixtures.ts, where createBdd(test) binds them to the framework's fixtures. The keyword in the feature file does not have to match: any step can follow Given, When, Then, And or But.

Context & users

Steps are separate functions, so they need a place to pass data along. Each scenario gets a fresh ctx object, the equivalent of Cucumber's "World".

interface ScenarioContext {
  user?: Account;            // who the scenario acts as
  newUser?: UserData;        // full data when registering through the UI
  addedProducts: { name; price }[];  // checked later by cart steps
  download?: Download;       // the invoice
}

One Given step decides which kind of user the scenario uses:

envUser

Given I use the account from the environment file

Your .env account. Shared and never deleted.

TC2, TC4, TC5

apiUser

Given a registered user exists

Created through the API before the scenario, deleted after it.

TC2b, TC16, TC20

newUser

Given I have details for a new user

Unique data; the scenario registers it in the UI. Deleted afterwards as a safety net.

TC1, TC14, TC15, TC23, TC24

Later steps such as I log in with the user's credentials and I am logged in as the user read ctx.user, so they work with all three kinds. If no user step ran, they fail with a message that says which step to add.

npm run test:cucumber:headed                      # watch the browser

npm run test:cucumber -- -g "Remove products"     # by scenario name
npm run test:cucumber -- -g "Saree"               # one Examples row
npm run test:cucumber -- --grep "@cart|@checkout" # several tags
npm run test:cucumber -- --grep @smoke --debug    # step through in the inspector

    Adding scenarios

    1. Write the scenario in the matching .feature file. Reuse sentences from the step catalogue where you can.
    2. Run npm run bddgen. For any sentence without a definition, it fails and prints a ready-made snippet.
    3. Paste the snippet into the matching steps/*.steps.ts file.
    4. Implement it with page-object calls and expect. If the page object lacks a locator or action, add it there, not in the step.
    5. Tag the scenario (@TCxx, and @smoke if it is a key path) and run it with --grep.
    // steps/cart.steps.ts
import { When, Then, expect } from '../fixtures/pomFixtures';

Then('the cart total is {string}', async ({ cartPage }, total: string) => {
  await expect(cartPage.grandTotal).toHaveText(total);   // locator lives in CartPage
});

    Writing good steps

    • Describe what the user does or sees, not how: I log in with the user's credentials, not I fill #email and click .btn.
    • Put values in quotes so one step serves many scenarios: the listing title is "Women - Tops Products".
    • Use one-step preconditions for setup a scenario does not test, such as I add a product to the cart, and detailed steps for what it does test.
    • Keep each sentence unique. Two patterns that match the same text make bddgen fail with an "ambiguous step" error.

    Pitfalls

    • Running stale tests.Plain npx playwright test runs the last generated files. After editing a feature, run npm run bddgen or use npm run test:cucumber.
    • Feature-file line numbers do not work as filters.cart.feature:29 refers to the generated file. Filter by tag or scenario name.
    • Data does not carry between scenarios.ctx is new for every scenario, and scenarios run in parallel in any order. Each scenario must set up what it needs.
    • Selectors creeping into steps.A step that calls page.locator(...) works today and breaks with the next markup change. Keep locators in page objects.
    • Test explorer is empty in VS Code.Enable tests/CucumberFramework/playwright.config.ts in the Playwright config selector and run npm run bddgen once.
