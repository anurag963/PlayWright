Automation Exercise Hybrid Cucumber Framework

The hybrid UI + API framework with a Gherkin layer on top. Scenarios mix both layers in plain language, and every sentence says which one it uses: via the API or in the UI.

4 feature files20 scenarios24 tests51 step definitions1 shared session~44 s full run

Overview

This framework combines two that already exist in the repo:

  • From the hybrid framework: page objects for the UI, REST and storefront clients for the API, all running on one browser session.
  • From the Cucumber frameworks: playwright-bdd, feature files, step definitions, a per-scenario ctx and the Cucumber HTML report.

The result is a scenario that a tester or product owner can read, where the API sets things up and the browser does the part being tested:

@HY18 @smoke
Scenario: Order placed in the UI from a cart built via the API
  Given a registered user exists
  When I log in via the API
  And I add the product at position 1 to the cart via the API with quantity 2
  And I proceed to checkout in the UI
  Then the UI order review lists the added products with their API prices

The site's API cannot create products; the catalogue is fixed. "Add a product via the API" means adding it to the cart over HTTP and checking it in the browser (HY1).

Generated files are gitignored and recreated on every run. Edit the feature or the step, never the generated file. Plain npx bddgen from the repo root does not generate these; use npm run bddgen:hybrid.

One shared session

The API clients are built on page.request, the browser context's own HTTP client, which uses the tab's cookies. The site keeps the cart and login in the session cookie, so a step in one layer changes what the next step in the other layer sees:

Sentence to code

The layer word in the sentence tells you which fixture the step uses. A "via the API" step calls an API client; an "in the UI" step calls a page object.

Feature file

When I add product 1 to the cart via the API
And I remove product 1 from the cart in the UI
Then the API cart contains exactly the added products

Step definitions

When('I add product {int} to the cart via the API',
  async ({ ctx, apiCart }, id) => { ... });

When('I remove product {int} from the cart in the UI',
  async ({ ctx, cartPage }, id) => { ... });

Context across layers

Each scenario gets a fresh ctx, Cucumber's "World". In this framework it also carries state from one layer to the other:

interface ScenarioContext {
  user?: Account;          // who the scenario acts as
  userData?: UserData;     // full data for UI forms and API comparisons
  products: Product[];     // last API list or search
  brands: string[];        // API brand names
  added: { id; quantity; product? }[];  // cart changes from EITHER layer
  apiOrder?: { amount; text };          // order paid via the API
  download?: Download;     // invoice downloaded in the UI
}

Because both layers write to and read from the same list, a scenario can change the cart in one layer and check it in the other with no extra wiring.

A step that needs data an earlier step should have set fails with a message naming that step, for example No product at position 1 (list has 0). Get products from the API first.

    Adding scenarios

    1. Write the scenario in the matching feature file. Put the layer in every sentence: "via the API" or "in the UI".
    2. Use API steps for setup the scenario doesn't verify (user, login, cart); use the UI for the behaviour under test.
    3. Run npm run bddgen:hybrid. For any sentence without a definition it fails and prints a snippet.
    4. Implement the step with a page object or API client. Record cart changes in ctx.added; poll in API checks that follow a UI click.
    5. Tag it with the next @HYxx and run it with --grep.
    // steps/cart.steps.ts
When('I remove product {int} from the cart via the API', async ({ ctx, apiCart }, id: number) => {
  expect(await apiCart.remove(id)).toBe('Cart removed');
  ctx.added = ctx.added.filter((a) => a.id !== id);   // keeps both layers' checks in step
});

    Pitfalls

    • Using the request fixture in a step.It has its own cookie jar, so a cart filled with it never reaches the browser. Use the API fixtures, which run on page.request.
    • Checking the API right after a UI click."Add to cart" in the UI is an AJAX call. API check steps poll with expect.poll; a new one should too.
    • Forgetting ctx.added.A step that changes the cart without recording it makes every later "cart contains" check fail, in both layers.
    • Guest cart after login.The site merges a guest cart into the user's cart when the cart page is opened. Open the cart page in the UI before going straight to checkout.
    • Running stale tests.Plain npx playwright test runs the last generated files. After editing a feature, run npm run bddgen:hybrid.
    • Scenarios listed twice in VS Code.The suite is already in the root config. Don't also enable this folder's own config in the config selector.
