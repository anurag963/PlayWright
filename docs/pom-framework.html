Automation Exercise POM Framework

A Playwright + TypeScript Page Object Model suite for automationexercise.com. This guide explains how the pieces fit together, what happens when a test runs, and how to add more.

27 tests26 site test cases11 page objects2 components3 reporters

Overview

The Page Object Model separates what a test checks from how the page is driven. Specs read like the site's own test case steps. Every selector and click lives in a page class, so a change to the site's markup is fixed in one place.

On top of plain POM, the framework adds four things:

  • Fixtures that hand each test ready-made page objects and test users, so specs never call new HomePage(page).
  • An API helper that creates and deletes accounts through the site's public API, which is much faster than doing it in the UI.
  • Flows that bundle multi-page journeys used by several tests, such as register or delete account.
  • A .env file that holds the base URL and the shared login. It is gitignored.

Architecture

Each layer only talks to the layer below it. Specs never touch selectors, and page objects never contain assertions about business rules.

Page objects

Every page inherits from BasePage. Locators are readonly fields set in the constructor; actions are async methods named after what a user does. Header and footer are composed in rather than inherited, because they are separate parts of the screen.

Code walkthrough

1. A spec asks for what it needs

Fixture names in the test's parameters decide what gets built. Here the test gets four page objects and a throwaway user that already exists on the site.

import { test, expect } from '../fixtures/pomFixtures';

test('TC16: Place Order: Login before Checkout', async ({
  homePage, loginPage, cartPage, paymentPage, apiUser, ...
}) => {
  await homePage.header.goToSignupLogin();
  await loginPage.login(apiUser.email, apiUser.password);
  await expect(loggedInText(homePage.header, apiUser.name)).toBeVisible();
  ...
});

2. The fixture builds and cleans up

Code before use() is setup; code after it is teardown. Teardown runs even if the test fails.

apiUser: async ({ api }, use) => {
  const user = createUser();             // unique email per run
  await api.createAccount(user);         // setup via API
  await use(user);                       // test runs here
  await api.deleteAccount(user.email, user.password);  // teardown
},

3. The page object hides the selectors

export class LoginPage extends BasePage {
  protected readonly path = '/login';
  readonly loginEmail = ...('[data-qa="login-email"]');

  async login(email: string, password: string) {
    await this.loginEmail.fill(email);
    await this.loginPassword.fill(password);
    await this.loginButton.click();
  }
}

The site has data-qa attributes on most form fields, so the framework uses those first. They are the selectors least likely to change.

Test users

Many site test cases end with "Delete Account". If every test used your account, the first one would delete it and the rest would fail. So there are three kinds of user:

envUser

Your account from .env. Shared by all runs and never deleted.

TC2, TC4, TC5

apiUser

Created through the API before the test, deleted after it. For tests that need an existing account.

TC2b, TC16, TC20

newUser

Unique data only; the test registers it through the UI. Deleted after the test in case the test failed early.

TC1, TC14, TC15, TC23, TC24

Unique emails (timestamp plus a random number) mean tests can run in parallel without clashing.

Design decisions

  • Ads are blocked at the network level.The site loads Google ads and full-screen vignettes that cover buttons. The page fixture aborts requests to ad domains, so clicks land where expected.
  • Navigation waits for the page's load event.The site attaches its jQuery handlers at the bottom of each page, after a slow Google Maps script. Clicking before that broke search, the category menu, the cart pop-up and the contact form. clickAndWaitForLoad() in BasePage and navigate() in the header handle this.
  • Setup goes through the API.Creating a user in the UI takes about 15 form steps. Tests that only need an existing account get one from the API in under a second.
  • The login is checked before any test runs.If .env has the wrong password, global setup stops the run with one clear message instead of a dozen failed login tests.
  • TC9 searches for "Jeans".The site's search also matches category names, so "Top" returns shirts from the Kids "Tops & Shirts" category.
  • Order success is checked on the confirmation page.The "Your order has been placed successfully!" message only flashes before the page changes, so tests check the "Order Placed!" heading instead.

Adding tests

A test on an existing page

  1. Open the matching spec in specs/, or create specs/<area>.spec.ts.
  2. Import test and expect from ../fixtures/pomFixtures.
  3. Name the page objects and user you need in the test's parameters.
  4. Call page actions and assert on page locators. Keep selectors out of the spec.

A new page

  1. Create pages/NewPage.ts extending BasePage with a path.
  2. Add locators as readonly fields, preferring data-qa, then ids, then roles and text.
  3. Use clickAndWaitForLoad() for clicks that open a new page.
  4. Register it in fixtures/pomFixtures.ts: add the type and a one-line fixture.
// fixtures/pomFixtures.ts
type PomFixtures = { ...; newPage: NewPage };
newPage: async ({ page }, use) => use(new NewPage(page)),

Running & reports

npm run test:framework              # headless, all tests
npm run test:framework:headed       # watch the browser
npx playwright test -c tests/Framework -g "TC14"   # one test

npm run report:framework            # Playwright HTML report
npm run test:framework:allure       # clean, run, build and open Allure
npm run allure:report               # build and open Allure from last results
ReporterOutputUse it for
listterminalLive progress while tests run
HTMLplaywright-report/frameworkDebugging a failure with trace, video and screenshot
Allureallure-results → allure-reportSharing results grouped by epic, feature and TC tag, with run history

Passing --reporter=... on the command line replaces all three configured reporters, so no Allure results are written. Use the npm scripts instead.

Locally a failed test is retried once (twice on CI). A trace is recorded on the retry, and screenshots and video are kept for failures.
